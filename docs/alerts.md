## Как это устроено

Алерты считает Grafana (unified alerting): правила лежат в
`grafana/provisioning/alerting/rules.yml` и при старте попадают в
**Grafana → Alerting → Alert rules → папка UPS**. Данные для правил Grafana
берёт из Prometheus, поэтому алерты работают, даже если их никто не открывает.

Состояния правила: `Normal` → `Pending` (условие выполняется, идёт отсчёт
`for`) → `Alerting` (сработало) → `Normal` (восстановилось).
При восстановлении отправляется сообщение «resolved».

## Семь правил

| Правило | Когда срабатывает | Держится | Важность |
|---|---|---|---|
| **ИБП недоступен по SNMP** | `up{job="snmp"}` меньше 1 — устройство не отвечает | 3 мин | critical |
| **ИБП работает от батареи** | `upsOutputSource == 5` — пропало питание | 1 мин | critical |
| **Низкий заряд батареи** | `upsBatteryStatus >= 3` (batteryLow / batteryDepleted) | 5 мин | critical |
| **Мало времени автономной работы** | остаток < 10 мин **и** питание от батареи | 2 мин | critical |
| **Высокая нагрузка на ИБП** | `upsOutputPercentLoad > 85` | 10 мин | warning |
| **Перегрев батареи** | `upsBatteryTemperature > 40` °C | 10 мин | warning |
| **Опрос ИБП стал медленным** | `snmp_scrape_duration_seconds > 10` | 10 мин | warning |

Что делать при срабатывании:

* **недоступен** — проверить питание ИБП, доступность по сети, включён ли SNMP
  и совпадает ли community (см. [troubleshooting.md](troubleshooting.md));
* **от батареи** — питание пропало; следите за остатком времени и готовьте
  корректное выключение оборудования;
* **низкий заряд** — батарея изношена или её пора менять;
* **мало времени** — осталось меньше 10 минут, планируйте отключение;
* **высокая нагрузка** — при переходе на батарею ИБП не вытянет нагрузку;
* **перегрев** — проверить вентиляцию и состояние батарей;
* **медленный опрос** — растёт нагрузка на `snmp_exporter`, см.
  [scaling.md](scaling.md).

## Почему недоступный ИБП «исчезает» из метрик

Если ИБП перестал отвечать по SNMP, то **все** метрики `ups*` у него исчезают —
остаётся только `up = 0`. Панели дашборда в этом случае показывают «No data»,
а не «0», и устройство выпадает из таблицы-сводки.

Именно поэтому:

* главное правило — «ИБП недоступен по SNMP» (ловит `up = 0`);
* на дашборде сверху есть панели **«Доступность ИБП (SNMP)»** и
  **«История доступности ИБП»** — по ним видно, кто именно пропал;
* в таблице-сводке есть строка `up` («Доступность (1 = ок)»).

По той же причине у всех правил стоит `noDataState: OK`: отсутствие данных
трактуется как «правило не сработало». Если устройство убрали из `targets.yml`,
алерт не останется висеть в состоянии «нет данных». Факт недоступности — это
именно `up = 0`, а не пропажа метрик.

## Уведомления в Telegram

По умолчанию уведомления **выключены**: правила считаются и видны в интерфейсе,
но сообщения никуда не отправляются, контакт-поинт не создаётся.

Включить:

1. Создайте бота у [@BotFather](https://t.me/BotFather) → получите токен вида
   `123456789:AA...`.
2. Узнайте id чата: напишите боту [@userinfobot](https://t.me/userinfobot) или
   добавьте бота в нужную группу — id группы отрицательный
   (например `-1001234567890`).
3. Пропишите значения в `.env` и перезапустите:

```bash
sudo sed -i 's|^TELEGRAM_BOT_TOKEN=.*|TELEGRAM_BOT_TOKEN=123456789:AA...|;
             s|^TELEGRAM_CHAT_ID=.*|TELEGRAM_CHAT_ID=-1001234567890|' \
     /opt/ups-monitoring-native/.env
sudo systemctl restart ups-monitoring
```

При старте `run.sh` сообщит: `[+] Уведомления: Telegram включён`.

Выключить обратно: очистите значения в `.env` и перезапустите — `run.sh` удалит
сгенерированные файлы уведомлений (файл, отредактированный вручную, не трогается).

Политика уведомлений (в `policies.yml`, создаётся автоматически): группировка по
правилу и устройству — одно сообщение на ИБП, а не общий поток; для `critical`
повтор раз в час, для `warning` — раз в 4 часа.

## Проверка, что уведомления работают

```bash
# токен и chat id подставились?
sudo grep TELEGRAM /opt/ups-monitoring-native/.env

# контакт-поинт есть в Grafana?
curl -s -u admin:ПАРОЛЬ localhost:3000/api/v1/provisioning/contact-points

# отправить тестовое сообщение
curl -s -u admin:ПАРОЛЬ -X POST localhost:3000/api/alert-notifications/test \
  -H 'Content-Type: application/json' -d '{"receivers":[{"name":"telegram"}]}'
```

Если сообщение не пришло — проверьте id чата (бот должен быть добавлен в чат и
иметь право писать) и состояние правил в **Grafana → Alerting → Alert rules**.

Посмотреть, что происходит с правилами прямо сейчас:

```bash
curl -s -u admin:ПАРОЛЬ localhost:3000/api/prometheus/grafana/api/v1/rules \
  | jq -r '.data.groups[].rules[] | "\(.name): \(.state)"'
```

## Тишина и пауза

* **Тишина (Silence)** — «не беспокоить по этому устройству N часов»: в Grafana
  **Alerting → Silences → New silence**, в matcher укажите `instance` = имя ИБП.
  Удобно на время плановых работ.
* **Пауза правила** — **Alerting → Alert rules → нужное правило → Pause**:
  правило перестаёт считаться и уведомлять (состояние сбрасывается).
* Не хотите уведомлений совсем — очистите `TELEGRAM_*` в `.env` (см. выше).

## Изменить порог или добавить правило

Все правила — в `grafana/provisioning/alerting/rules.yml`, каждое состоит из
запроса (`data → refId: A`) и условия (`threshold`). Например, порог нагрузки:

```yaml
        data:
          - refId: A
            model:
              expr: 'upsOutputPercentLoad > 85'      # ← что считаем
...
                - evaluator: {params: [85], type: gt} # ← порог срабатывания
```

Порядок правки:

```bash
sudo vi /opt/ups-monitoring-native/grafana/provisioning/alerting/rules.yml
sudo systemctl restart ups-monitoring         # правила читаются при старте Grafana
```

Проверка: **Grafana → Alerting → Alert rules → UPS** — правило появилось с новым
порогом, состояние `Normal`. Если правила нет совсем — смотрите
`data/grafana.log` (ошибка в YAML не даёт Grafana загрузить провижининг).

Добавить своё правило проще всего копированием блока `- uid: ...` целиком:
замените `uid`, `title`, `expr`, `for`, `labels.severity` и порог в
`evaluator.params`.
