## Каждый день

```bash
/opt/ups-monitoring-native/status.sh      # 30 секунд: всё ли живо и отвечает
```

Скрипт показывает: запущены ли три сервиса и отвечают ли они по HTTP, сколько
ИБП в списке, сколько правил алертов, включены ли уведомления и сколько
хранится история. Если всё в порядке — больше ничего не требуется.

Дашборд: `http://<IP-сервера>:3000` → **«ИБП — обзор»**. Сверху — счётчики по
всему парку (всего, в сети, нет связи, от батареи, тревоги) и таблица «один ИБП =
одна строка», ниже — вкладка на каждое устройство с текущими значениями и
графиками. Состав, пороги и трактовка — [docs/dashboard.md](dashboard.md).

## Команды управления

| Действие | systemd | без systemd |
|---|---|---|
| Запустить | `sudo systemctl start ups-monitoring` | `./run.sh` |
| Перезапустить (применить конфиги) | `sudo systemctl restart ups-monitoring` | `./stop.sh && ./run.sh` |
| Остановить | `sudo systemctl stop ups-monitoring` | `./stop.sh` |
| Состояние | `sudo systemctl status ups-monitoring` | `./status.sh` |
| Автозапуск | `sudo systemctl enable/disable ups-monitoring` | — |

Сколько ждать завершения перед `SIGKILL`, задаёт сам `stop.sh`:
`./stop.sh --timeout 30` (по умолчанию 20 секунд) — `run.sh` этот параметр не
передаёт, поэтому скрипты остаются совместимыми с прежними версиями.

Все команды выполняются в каталоге `/opt/ups-monitoring-native`.

## Логи

Логи лежат в каталоге `LOG_DIR` — по умолчанию это `<каталог установки>/data`
(то есть `/opt/ups-monitoring-native/data`), но его можно вынести на другой диск
(см. [ниже](#данные-и-логи-на-разных-дисках)). Текущий путь всегда видно в
`./status.sh` и в итоговом выводе `./run.sh`.

| Файл | Что внутри |
|---|---|
| `LOG_DIR/grafana.log` | Grafana: старт, провижининг, алерты, ошибки |
| `LOG_DIR/prometheus.log` | Prometheus: старт, запись блоков, ошибки опроса |
| `LOG_DIR/snmp_exporter.log` | snmp_exporter: **каждая неудачная попытка опроса** |
| `LOG_DIR/snmp_exporter-N.log` | то же для шарда N (когда `SNMP_SHARDS > 1`) |
| `LOG_DIR/grafana/` | только если включён файловый лог Grafana (`GF_LOG_MODE=console file`) |
| `journalctl -u ups-monitoring` | только сообщения супервизора `run.sh` |

```bash
cd /opt/ups-monitoring-native
tail -f data/*.log                 # каталог по умолчанию
./status.sh                        # если LOG_DIR вынесен — покажет актуальный путь

# кто не отвечает и почему
grep 'Error scraping' data/snmp_exporter*.log | tail -20
```

Если `LOG_DIR` вынесен на другой диск, подставьте свой путь — он напечатан в
`./status.sh` в блоке «Логи (<каталог>)» вместе с размерами файлов.

Рабочая конфигурация Prometheus — `data/prometheus.yml` (внутри `DATA_DIR`): она
собирается при каждом запуске из `prometheus.yml` (подставляются адреса процессов
`snmp_exporter` и правила шардинга). Правки в неё вносить бессмысленно — они
исчезнут при следующем запуске; правьте исходный `prometheus.yml`.

## Ротация логов по размеру

Логи не растут бесконечно: при запуске `run.sh` поднимает фоновый ротатор
(`run.sh --rotate-daemon`), который раз в `LOG_CHECK_INTERVAL` секунд смотрит
размеры файлов в `LOG_DIR`.

Когда файл дорастает до `LOG_MAX_SIZE` (по умолчанию 10 МБ), он **обрезается на
месте**: самая старая часть стирается, а хвост — последние `LOG_KEEP_PERCENT` %
(по умолчанию 10 %) — остаётся. То есть в файле всегда лежит свежая история, а
сервис продолжает писать в тот же файл (логи открыты в режиме `O_APPEND`),
перезапуск не нужен.

```ini
LOG_MAX_SIZE=10M        # предел на файл считая хвост; 0 — не ограничивать
LOG_KEEP_PERCENT=10     # сколько процентов хвоста оставить при обрезке (0 — обнулять)
LOG_CHECK_INTERVAL=10   # как часто проверять размеры, секунды (минимум 5)
```

Что важно знать:

* размер проверяется **периодически**, поэтому лог может перерасти предел на
  «скорость записи × `LOG_CHECK_INTERVAL`» — для болтливого сервиса уменьшите
  `LOG_CHECK_INTERVAL` (минимум 5 с);
* `LOG_KEEP_PERCENT=0` обнуляет файл целиком (старые записи теряются сразу);
* изменить настройки — правка `.env` и перезапуск
  (`sudo systemctl restart ups-monitoring`): ротатор читает `.env` при старте;
* если ротатор не работает (например, стек подняли очень старым `run.sh`),
  `status.sh` пишет «ротатор НЕ запущен», и логи растут без обрезки.

Дополнительно установщик создаёт правило `/etc/logrotate.d/ups-monitoring`
(неделя на файл, 8 архивов, сжатие) — оно убирает старое в архив `.1…8.gz`.
Проверить:

```bash
sudo logrotate -d /etc/logrotate.d/ups-monitoring
```

Обрезать логи прямо сейчас (не дожидаясь ротатора) — одной командой; пригодится
также из cron или systemd-таймера:

```bash
./run.sh --rotate-now
```

## Данные и логи на разных дисках

По умолчанию и история, и логи лежат в `<каталог установки>/data`. Если на
сервере два диска (например, быстрый SSD и большой HDD), каталоги можно
разнести — задаются в `.env` (или флагами установщика `--data-dir`/`--log-dir`):

```ini
DATA_DIR=/mnt/disk1/ups-monitoring       # история Prometheus, база Grafana, pid-файлы сервисов
LOG_DIR=/mnt/disk2/ups-monitoring-logs   # логи сервисов, pid-файл ротатора (rotate.pid)
```

### Как выбрать диск

Решающих признаков три: **как много пишется**, **что будет, если диск переполнится**
и **переживёт ли данные перезагрузку**.

| Что | Объём и характер записи | Куда класть |
|---|---|---|
| `DATA_DIR` (история Prometheus, база Grafana) | пишется постоянно (блоки TSDB каждые ~2 часа), за год ~1.5 ГБ на 10 ИБП, ~30 ГБ на 200 | быстрый диск (SSD), достаточно места под весь срок хранения `RETENTION_TIME` |
| `LOG_DIR` (логи) | почти всегда тишина; пишется при ошибках опроса, объём ограничен `LOG_MAX_SIZE` | любой диск, кроме системного; SSD не нужен |

Отсюда практические правила:

* **Логи — не на системный диск (`/`).** Основной смысл выноса именно в этом:
  когда ИБП пропадает, `snmp_exporter` пишет ошибку на каждый опрос, и логи
  первыми съедают место — а вместе с ними встанут и система, и сам мониторинг.
  Отдав логи отдельному диску (или хотя бы отдельной файловой системе), вы
  изолируете «шумный» рост от истории и от системы.
* **Много ИБП (десятки-сотни) или частый опрос** — историю на SSD: Prometheus
  пишет непрерывно и на HDD с медленным случайным вводом-выводом будет
  отставать. Логи даже у сотни устройств остаются мизерными.
* **Один диск** — оставьте значения по умолчанию (`DATA_DIR`/`LOG_DIR` не
  задавайте) и просто задайте `LOG_MAX_SIZE` (например, `50M`): место под логи
  ограничено ~`LOG_MAX_SIZE × (1 + 8 архивов logrotate) ≈ 450 МБ` на файл.
* **Сколько нужно места под логи**: считайте по размеру файлов в `status.sh`:
  `snmp_exporter*.log` + `prometheus.log` + `grafana.log`. Потолок — около
  `LOG_MAX_SIZE × число файлов × (1.2 + архивы)`. Для 4 процессов и 10 МБ это
  меньше 100 МБ, то есть отдельный диск под логи имеет смысл только ради
  изоляции, а не ради объёма.
* **Не используйте для этих каталогов**: tmpfs `/run` (логи и история исчезнут
  после перезагрузки) и сетевые ФС (NFS/SMB: Prometheus не поддерживает работу
  TSDB на них, а недоступная шара приведёт к ошибкам записи). Обычный локальный
  раздел (ext4/xfs) — то, что нужно.
* **Диск должен монтироваться до запуска стека** (запись в `/etc/fstab` или
  systemd-mount; для второго диска полезен `nofail`, чтобы сервер поднялся даже
  при сбое диска — но тогда обязательно см. предупреждения ниже).

```bash
sudo vi /opt/ups-monitoring-native/.env
sudo systemctl restart ups-monitoring
/opt/ups-monitoring-native/status.sh     # покажет «Логи (<каталог>)» и «данные (...):»
```

Нюансы:

* каталоги создаются автоматически, права нужны только на запись (стек работает
  от root, поэтому обычно проблем нет);
* **диск должен быть смонтирован до запуска**: если `/mnt/disk2` не смонтирован,
  каталог создастся на системном диске и логи уедут туда. `run.sh` и `install.sh`
  предупреждают об этом («оказался на системном диске (/)»), проверяйте
  `findmnt -T /mnt/disk2/ups-monitoring-logs`;
* перенос уже накопленных данных — обычное `mv` при остановленном стеке:

```bash
sudo systemctl stop ups-monitoring
sudo mv /opt/ups-monitoring-native/data /mnt/disk1/ups-monitoring
# прописать DATA_DIR=/mnt/disk1/ups-monitoring в .env
sudo systemctl start ups-monitoring
```

Если после переноса забыть поправить `.env`, старый каталог просто останется
мусором на прежнем диске, а стек начнёт с чистой истории — проверяйте
`status.sh` после переноса.

## Сколько места занимает история

История Prometheus лежит в `DATA_DIR/prometheus` (по умолчанию
`/opt/ups-monitoring-native/data/prometheus`; каталог можно вынести на отдельный
диск — см. [выше](#данные-и-логи-на-разных-дисках)). На одно устройство
приходится ≈30 временных рядов, поэтому места уходит мало:

| Устройств | Данных в сутки | За год (примерно) |
|---|---|---|
| 10 | ~5 МБ | ~1.5 ГБ |
| 50 | ~25 МБ | ~8 ГБ |
| 200 | ~100 МБ | ~30 ГБ |

Ориентируйтесь на реальные цифры: `du -sh /opt/ups-monitoring-native/data/prometheus`.

Как изменить срок хранения — в `.env` (нужен перезапуск):

```ini
RETENTION_TIME=1y        # 15d, 90d, 1y, 5y
RETENTION_SIZE=10GB      # необязательное ограничение по объёму
```

Проверка: `./status.sh` показывает «хранение истории Prometheus: …», либо

```bash
curl -s localhost:9090/api/v1/status/flags | jq -r '.data."storage.tsdb.retention.time"'
```

## Бэкап и восстановление

Стоит сохранять (это небольшой набор файлов — секунды на копирование):

| Что | Зачем |
|---|---|
| `.env` | пароль Grafana, токен Telegram, порты |
| `targets.yml` | список ИБП — единственная копия инвентаря |
| `snmp.yml` | community/SNMP v3, набор OID |
| `grafana/provisioning/` | правила алертов, уведомления, источники данных |
| `grafana/dashboards/` | дашборд (если правили через UI) |

Историю метрик (`data/prometheus`) и базу Grafana (`data/grafana`) бэкапить
обычно не нужно — после восстановления они наполнятся заново.

```bash
# бэкап конфигов
sudo tar czf /root/ups-config-$(date +%F).tar.gz -C /opt/ups-monitoring-native \
     .env targets.yml snmp.yml prometheus.yml grafana

# восстановление на чистой машине
curl -fsSL .../install.sh | sudo bash -s -- --yes --no-start
sudo tar xzf /root/ups-config-2026-01-01.tar.gz -C /opt/ups-monitoring-native
sudo systemctl restart ups-monitoring
```

## Обновление и смена версий

Обновление кода и конфигов — повторным запуском установщика (см.
[install.md](install.md#обновление)).

Версии бинарников заданы в начале `run.sh`:

```bash
SNMP_VER="0.26.0"
PROM_VER="3.1.0"
GF_VER="11.5.1"
```

Чтобы обновиться до новых версий: поменяйте их в репозитории (или прямо на
сервере), удалите соответствующий каталог в `bin/` и перезапустите — `run.sh`
скачает новую версию:

```bash
sudo rm -rf /opt/ups-monitoring-native/bin/prometheus-3.1.0.linux-amd64
sudo vi /opt/ups-monitoring-native/run.sh          # вписать новую, например PROM_VER="3.2.0"
sudo systemctl restart ups-monitoring
```

Бинарники скачиваются с официальных источников (GitHub Releases Prometheus и
dl.grafana.com). Установщик дополнительно сверяет sha256; `run.sh` при
самостоятельной загрузке — нет, поэтому после установки новых версий через
`run.sh` проверьте логи: сервис должен подняться и отвечать (`./status.sh`).

## После перезагрузки сервера

Ничего делать не нужно: systemd поднимает стек автоматически
(`systemctl is-enabled ups-monitoring` → `enabled`). Проверка после ребута:

```bash
systemctl status ups-monitoring --no-pager
/opt/ups-monitoring-native/status.sh
```

Первый опрос всех ИБП происходит в течение минуты после старта (плюс время на
загрузку истории из базы).

## Смена пароля Grafana

```bash
sudo sed -i 's|^GRAFANA_ADMIN_PASSWORD=.*|GRAFANA_ADMIN_PASSWORD=НовыйПароль|' \
     /opt/ups-monitoring-native/.env
sudo systemctl restart ups-monitoring
```

Пароль применяется к пользователю `admin` (или тому, что в `GRAFANA_ADMIN_USER`)
при старте. Если пароль меняли и в интерфейсе, файл `.env` всё равно остаётся
источником истины при следующем старте.

## Следить за самим мониторингом

Если упадёт сервер мониторинга, об этом никто не узнает — ни один алерт не
уйдёт. Простое решение: внешняя проверка с другой машины.

```bash
# с любого другого сервера: раз в 5 минут проверяем, что мониторинг отвечает
*/5 * * * * curl -fsS --max-time 10 http://ups-host:3000/api/health >/dev/null \
            || echo "UPS monitoring недоступен" | mail -s "ALERT" admin@example.com
```

Более правильный вариант — второй Prometheus (или Zabbix/другой мониторинг) с
запросом `up{job="snmp"} == 0` по этому серверу.
