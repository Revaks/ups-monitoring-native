## Сколько выдержит один сервер

| Устройств | Что нужно |
|---|---|
| до 50 | ничего, работает «как есть» (интервал 1 минута) |
| 50–200 | проверить `snmp_scrape_duration_seconds`; при росте — увеличить интервал до 2–5 минут |
| 200–500 | `SNMP_SHARDS=2..4` в `.env` и/или интервал 5 минут |
| больше 500 | несколько серверов сбора (или один, но с интервалом 5–10 минут, шардингом и запасом CPU) |

Практическая формула для одного `snmp_exporter`:

```
устройств ≈ (интервал опроса, с) × 0.5 / (среднее время опроса одного ИБП, с)
```

Замеры на локальной сети: один ИБП опрашивается ~40 мс (идеальный случай,
эмулятор), реальные устройства — обычно 100–300 мс. При 200 мс и интервале 60 с
получается `60 × 0.5 / 0.2 ≈ 150` устройств на процесс, дальше нужен запас
(ниже — как делить).

Проверка текущей загрузки:

```bash
curl -s 'localhost:9090/api/v1/query?query=snmp_scrape_duration_seconds' \
  | jq -r '.data.result[] | "\(.metric.instance) \(.value[1]) s"'
```

Если у устройств стабильно больше 5 секунд — пора либо увеличить интервал, либо
делить опрос между несколькими экспортёрами. На это же есть алерт
«Опрос ИБП стал медленным» (>10 с в течение 10 минут).

## Что ограничивает

1. **Один `snmp_exporter`** — все запросы Prometheus идут в него. Он держит
   параллельные опросы нормально, но упирается в CPU и в SNMP-таймауты. Лечится
   шардингом (`SNMP_SHARDS`, см. ниже).
2. **SNMP по UDP**: потери пакетов и медленные устройства тянут время опроса.
3. **Недоступные устройства**: каждое такое устройство занимает поток до
   `timeout × (retries + 1)` секунд (см. ниже).
4. **Интервал опроса**: чем чаще опрашивать, тем больше параллельной работы.

## Таймауты: почему недоступные ИБП дорогие

В `snmp.yml`:

```yaml
    retries: 1
    timeout: 2s
```

Худшее время опроса одного недоступного ИБП = `2s × (1 + 1) = 4s`. Если из 200
устройств 50 отключены (узел без питания), то в каждом цикле 50 опросов идут по
4 секунды. Prometheus терпит это (`scrape_timeout: 30s`), но лишняя нагрузка
заметна.

Что можно сделать:

* уменьшить `timeout` до `1s` (если сеть быстрая) — худший случай станет 2 с;
* опрашивать отключённые устройства реже: вынести их в отдельный job с
  интервалом 5 минут (см. ниже), либо убрать из `targets.yml` — алерт всё равно
  придёт, если устройство пропадёт целиком… нет, не придёт: устройство без
  записи в `targets.yml` не опрашивается. Убирайте только выведенные из
  эксплуатации, а не временно выключенные.

## Разные интервалы опроса для разных ИБП

Если ИБП в ЦОД требуют опроса раз в 30 секунд, а устройства в дальних узлах —
раз в 5 минут, заведите два job в `prometheus.yml` и два файла со списками:

```yaml
scrape_configs:
  - job_name: 'snmp-critical'          # важные устройства
    scrape_interval: 30s
    metrics_path: /snmp
    params: {module: [ups], auth: [public_v2]}
    file_sd_configs:
      - files: ['targets-critical.yml']
    relabel_configs: [ … те же правила, что и в базовом job … ]

  - job_name: 'snmp'                   # остальные
    scrape_interval: 5m
    ...
```

Файлы со списками можно генерировать из одной таблицы инвентаря (см. ниже).
Помните: у алертов из Grafana своё время удержания (`for`), поэтому на редком
интервале правило «работа от батареи» может сработать чуть позже.

## Несколько snmp_exporter (шардинг)

Шардинг встроен: поставьте в `.env` число процессов — всё остальное `run.sh`
сделает сам.

```ini
SNMP_SHARDS=2      # 1 (по умолчанию) — один процесс, 2..8 — пул из N процессов
```

Что происходит при запуске:

* стартуют N процессов `snmp_exporter` на портах `SNMP_EXPORTER_PORT` … `+N-1`
  (по умолчанию 9116, 9117, …), у каждого свой pid-файл и свой лог
  `data/snmp_exporter-N.log`;
* `run.sh` собирает рабочую конфигурацию Prometheus в `data/prometheus.yml`
  (источник — `prometheus.yml`) и подставляет вместо одного адреса экспортёра
  правила `hashmod`, которые раскладывают ИБП по шардам;
* каждый процесс под присмотром супервизора: упавший перезапускается,
  `stop.sh` гасит все, `status.sh` показывает распределение.

Распределение детерминированное: адрес ИБП хэшируется, поэтому устройство
всегда попадает в свой шард, а история не «прыгает» между сервисами.

```bash
# посмотреть, сколько ИБП ушло в каждый шард
/opt/ups-monitoring-native/status.sh
#   распределение ИБП по шардам (штук:порт): 62:9116 58:9117
```

Сколько ставить:

| Устройств | `SNMP_SHARDS` |
|---|---|
| до ~150 | 1 |
| 150–400 | 2 |
| 400–800 | 3–4 |
| больше | 4–8 (максимум 8) + подумать про отдельные серверы сбора |

Практическое правило: суммарное время опроса всех устройств должно укладываться
в интервал с запасом ×2. Если по метрике `snmp_scrape_duration_seconds` видно,
что один процесс впритык — добавьте шард и перезапустите:

```bash
sudo sed -i 's/^SNMP_SHARDS=.*/SNMP_SHARDS=2/' /opt/ups-monitoring-native/.env
sudo systemctl restart ups-monitoring
curl -s localhost:9090/api/v1/targets \
  | jq -r '.data.activeTargets[].scrapeUrl' | sed 's|.*:\([0-9]*\)/snmp.*|\1|' | sort | uniq -c
```

Важно знать:

* при смене `SNMP_SHARDS` устройства перераспределяются — на дашборде это видно
  как разрыв только в служебных `snmp_scrape_*` метриках, история самих ИБП
  (`instance` = имя устройства) сохраняется;
* порты шардов должны быть свободны — `run.sh` предупредит, если заняты;
* `prometheus.yml` править по-прежнему нужно только в одном месте: рабочую копию
  в `data/` скрипт перезаписывает при каждом запуске (в ней же исправляется
  путь к `targets.yml` на абсолютный, иначе Prometheus не найдёт список ИБП).

### Если экспортёры должны быть на разных серверах

Схема с `hashmod` предполагает, что все экспортёры доступны по сети. Чтобы
опрашивать сегменты своими серверами, поставьте на каждом сегменте копию стека
(или только `snmp_exporter`), а в `prometheus.yml` основного сервера замените
`replacement: 127.0.0.1:9116` на адрес удалённого экспортёра:

```yaml
      - source_labels: [__address__]
        target_label: __param_target
      - source_labels: [ups_segment]
        regex: 'dc2'
        replacement: 10.10.0.5:9116        # экспортёр в другом сегменте
        target_label: __address__
```

Метку `ups_segment` задайте устройству в `targets.yml`. Так же удобно выносить
опрос филиалов, куда из центра ходить по SNMP нельзя.

## Список устройств: CSV и автоматизация

`targets.yml` — обычный файл, поэтому его можно генерировать чем угодно:

```bash
# из таблицы (Excel/NetBox/CMDB → CSV)
tools/targets-from-csv.sh inventory.csv

# из выгрузки в другом формате — своим скриптом, формат targets.yml прост:
#   - targets: [10.0.0.5]
#     labels: {ups_name: 'UPS-DC1', location: 'ЦОД-1'}
```

Альтернатива для больших и динамичных парков — `http_sd_configs`: Prometheus сам
забирает список по HTTP в формате JSON. Тогда источником истины становится ваш
сервис:

```yaml
    http_sd_configs:
      - url: http://inventory.example.com:8080/prometheus/ups-targets
        refresh_interval: 1m
```

Формат ответа — массив объектов `{"targets": ["10.0.0.5"], "labels": {"ups_name": "UPS-DC1"}}`.

## Диск и кардинальность метрик

На одно устройство приходится ≈30 временных рядов (метрики UPS-MIB + служебные
`snmp_scrape_*`, `up`, `scrape_*`). Это мало: 200 устройств — около 6000 серий,
это спокойно для одного Prometheus.

Оценка диска:

```
диск ≈ устройств × 0.5 МБ × дней
```

(200 устройств × 365 дней ≈ 35 ГБ). Точнее — по факту:

```bash
du -sh /opt/ups-monitoring-native/data/prometheus
```

Ограничения задаются в `.env` (`RETENTION_TIME`, `RETENTION_SIZE`), см.
[operations.md](operations.md#сколько-места-занимает-история).

## Когда выносить Prometheus и Grafana отдельно

Если устройств много (500+) или Grafana нужна нескольким командам, разумно
разделить роли:

* **сбор** — серверы в тех же сегментах сети, что и ИБП (по одному
  `snmp_exporter` на сегмент + Prometheus, который их опрашивает);
* **хранение и показ** — отдельный сервер с Grafana и Prometheus
  (можно с `remote_write`, если сборщиков несколько).

Проект запускает всё на одном хосте, поэтому такая схема потребует ручной
настройки: `snmp_exporter` и `Prometheus` ставятся в том же виде, меняется только
адрес в `__address__` (там, где сейчас `localhost:9116`) и, при необходимости,
адрес источника данных в `grafana/provisioning/datasources/datasource.yml`.
