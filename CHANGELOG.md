# История версий

Формат версий — [SemVer](https://semver.org/lang/ru/): `MAJOR.MINOR.PATCH`.
Каждая версия помечена тегом в git, поэтому любую из них можно поставить
повторно одной командой — в том числе предыдущую:

```bash
# поставить конкретную версию
curl -fsSL https://raw.githubusercontent.com/Revaks/ups-monitoring-native/main/install.sh \
  | sudo bash -s -- --yes --ref v1.0.0
```

Список версий: [Releases](https://github.com/Revaks/ups-monitoring-native/releases)
и `git tag -l`. Что именно поменялось — ниже.

## [1.6.0] — 2026-09-30

### Добавлено

* **Территории (площадки): метка `site` в `targets.yml`.** Метка отвечает на
  вопрос «кто это должен видеть», тогда как `location` — «где это стоит» (узел,
  шкаф, ряд). Сама по себе метка ничего не ограничивает: она нужна, чтобы пул ИБП
  можно было разделить по территориям и раздавать группам. Название — точное
  значение, а не шаблон: `Площадка №1` и `площадка 1` это разные территории.

* **Доступ групп по площадкам.** В `/root/groups.json` у группы появился ключ
  `sites` — список названий площадок, которые группа видит:

  ```json
  {"org": "Электрики", "slug": "electricians", "sites": ["Площадка №1"]}
  ```

  Скрипт сам собирает из списка выражение (с экранированием спецсимволов) и
  подставляет его во **все** запросы копии дашборда, включая счётчики, сводку по
  площадкам и timeline'ы, — группа электриков не увидит чужих ИБП даже в
  «Всего ИБП». Отдельно ограничиваются и списки в переменных дашборда, поэтому в
  выпадающих списках «Площадка» и «ИБП» чужих значений не появляется. Ограничение
  зашито в сами запросы, так что подмена `var-site` в адресе страницы результата
  не даёт. `sites` и прежний `location_filter` можно указывать вместе — тогда
  условия складываются.

* **Дашборд: переменная «Площадка»** (`site`) — фильтрует весь дашборд по
  территориям, включая список вкладок ИБП. У неё задан `allValue: ".*"`:
  если метки `site` нет ни у одного устройства, переменная пуста, но дашборд
  ведёт себя как раньше и показывает весь парк.

* **Дашборд: блок «Территории»** — сводка по площадкам, одна строка на
  территорию: всего ИБП, в сети, нет связи, от батареи, низкий заряд, перегрузка,
  тревоги. Панель всегда даёт разбивку целиком (переменная «Площадка» на неё не
  влияет), чтобы площадки можно было сравнивать между собой; права доступа её при
  этом ограничивают.

* **Дашборд: колонка «Площадка»** в таблице «Состояние всех ИБП».

* **Инвентарь CSV с шапкой и колонкой `site`.** Теперь можно писать
  `ip;site;name;location;snmp_auth`: колонки разрешается переставлять и указывать
  не все (обязательна только `ip`). Скрипт сообщает, сколько получилось площадок,
  и предупреждает, если ни у одного ИБП метки `site` нет.

### Изменено

* **Шаблон `targets.yml`: метка `site` появилась в примере и в комментариях.**
  Установщик генерирует этот файл сам (готовый `targets.yml` из репозитория не
  копируется), и раньше о территориях из него узнать было нельзя — теперь о
  метке и её роли написано там, где её будут искать. Существующие установки не
  затрагиваются: при обновлении файл остаётся прежним.

* **`tools/grafana-groups.py` проверяет конфигурацию до обращения к Grafana.**
  Опечатка в названии ключа, дубль `slug`, пустой список площадок, название вида
  `Площадка*` (звёздочка — признак попытки написать шаблон вместо точного
  значения) или группа вовсе без фильтра теперь дают понятное сообщение вместо
  молчаливой выдачи лишних прав.

* **CI: проверка PromQL включает выражения копий групп,** причём с названием
  площадки, содержащим спецсимволы RE2. Раньше проверялись только базовые
  дашборды, а именно в копиях выражение получает два матчера по одной метке
  (жёсткий фильтр группы рядом со ссылкой на переменную).

* Прежний формат инвентаря без шапки (`IP;имя;расположение[;snmp_auth[;snmp_module[;site]]]`)
  и ключ `location_filter` продолжают работать без изменений — существующие
  настройки групп переписывать не нужно.

### Исправлено

* **Названия площадок со спецсимволами RE2 ломали разбор выражения.**
  Спецсимволы (скобки, точки, `+`, `*`, `|`) нужно экранировать дважды: выражение
  попадает в строковый литерал PromQL, который сам разбирает escape-последовательности
  и одиночный `\(` отвергает с ошибкой «unknown escape sequence». Проверено
  `promtool check rules`: без удвоения площадка «Площадка №1 (основная)» ломала
  весь дашборд группы.

* **CHANGELOG: у версии 1.5.2 не было ссылки-определения** — заголовок не
  превращался в ссылку на релиз.

## [1.5.2] — 2026-09-30

### Исправлено

* **Дашборд: переход по имени ИБП больше не сбрасывает период.** Ссылка
  «Показать вкладку этого ИБП» в таблице парка вела на `/d/ups-overview/…` без
  сохранения времени, поэтому после клика графики показывались за диапазон по
  умолчанию (6 часов), а не за тот, который смотрел дежурный. У ссылки включён
  `keepTime` (проверено по исходникам Grafana 11.5.1: `panellinks/link_srv.ts`
  подставляет `$keepTime=true`, макрос разворачивается в `from`/`to`).
* **Копии дашборда для групп ссылались на базовый дашборд.** `tools/grafana-groups.py`
  пересобирает страницу группы под своим uid (`ups-engineers`, `ups-operators`…),
  но ссылка внутри копии оставалась на `ups-overview` — в организации группы
  такого дашборда нет, и клик по имени ИБП приводил к «Dashboard not found».
  Теперь копия переадресует ссылки на саму себя (`retarget_links`), в выводе
  скрипта видно число переадресованных ссылок. Действует после повторного
  запуска скрипта (см. [docs/access.md](docs/access.md)).

### Изменено

* **Дашборд «ИБП — обзор»: убраны плитки «Имя в ИБП» и «Производитель».** Обе
  показывали вместо значения служебное имя серии Prometheus вида
  `upsIdentName {__name__="upsIdentName", instance="…", …}`: строковые OID
  `upsIdentName` и `upsIdentManufacturer` у многих моделей пустые, метка в серию
  не попадает, `legendFormat` не может её подставить и Grafana откатывается к
  имени серии. Устройство и опрос тут ни при чём — показывать в плитках было
  нечего, поэтому они удалены, а оставшиеся плитки ряда сдвинуты влево
  («Сбоев входа» `x: 20 → 12`, «Модель» `x: 4 → 0`, «ПО ИБП» `x: 8 → 4`,
  «ПО SNMP-карты» `x: 12 → 8`), чтобы в ряду не осталось пустых клеток. Метрики
  `upsIdentName` и `upsIdentManufacturer` продолжают собираться: их видно в
  Explore и можно использовать в PromQL.
* Документация: `docs/dashboard.md` и `docs/configuration.md` больше не обещают
  плиток «Имя в ИБП» и «Производитель» и объясняют, почему их нет в паспорте
  устройства ([docs/dashboard.md](docs/dashboard.md)).
* `ROADMAP.md`: убран пункт «P0-3. Закрыть лишние порты» — решение по
  `LISTEN_ADDR` принимается на месте и в план работ не входит. Заодно в P2-1
  отмечено, что перечисленные там проверки в CI уже сделаны.

### Добавлено

* **`tools/check-dashboard.py` — семантические проверки дашбордов** (то, чего не
  видит `jq -e`): уникальность `panel id`, раскладка `gridPos` (панель влезает в
  сетку, соседи в ряду не перекрываются), все панели ходят в разрешённые
  источники данных (ловит «случайную» панель с `-- Grafana --` и Random Walk),
  внутренние ссылки ведут на существующий дашборд. Дополнительно скрипт собирает
  копии для групп через `make_group_dashboard` и проверяет, что ссылки в копии
  ведут на неё саму — именно эта проверка ловит ошибку из раздела «Исправлено».
* **`tools/check-versions.py` — версии и релизная гигиена.** Версии компонентов
  в документации, `.env.example` и шаблонах провижининга сверяются с `run.sh`
  (единственный источник правды: `SNMP_VER`/`PROM_VER`/`GF_VER`); строки вида
  «проверено на Grafana 11.5.1» и примеры («например `PROM_VER="3.2.0"`»)
  пропускаются как исторические. С `--tag vX.Y.Z` проверяется, что в `CHANGELOG.md`
  есть раздел для тега — CI запускает это на push тега, чтобы релиз не уезжал без
  записи.
* CI (`.github/workflows/ci.yml`): шаги «Семантика дашборда», «Версии в
  документации» и «CHANGELOG для тега»; `py_compile` теперь проверяет все
  `tools/*.py`, а не только `grafana-groups.py`.

## [1.5.1] — 2026-09-29

### Исправлено

* **`tools/grafana-groups.py`: падал с трассировкой сразу после `--restart`.**
  Ожидание «Grafana поднялась?» не переживало `Connection refused`: первый же

  недоступной Grafana печатается понятное сообщение с подсказкой, что делать,
  без трассировки. Проверено на сценарии «живая Grafana → перезапуск → порт
  закрыт 10 секунд → снова жива»: скрипт дожидается и выставляет лендинги.
  Дополнительно: недоступность Grafana на старте теперь тоже даёт внятную
  ошибку вместо трейсбека.
* **`tools/grafana-groups.py`: пароли новых аккаунтов печатаются сразу при
  создании.** Раньше они выводились только в итоговой сводке в самом конце, и
  падение на любом следующем шаге означало, что пароли созданных аккаунтов
  потеряны безвозвратно. Теперь пароль виден в строке про создание аккаунта.

## [1.4.0] — 2026-09-29

### Добавлено

* **Логи не растут бесконечно: обрезка по размеру.** `run.sh` поднимает фоновый
  ротатор (`run.sh --rotate-daemon`), который раз в `LOG_CHECK_INTERVAL` секунд
  смотрит размеры файлов и, когда лог дорастает до `LOG_MAX_SIZE` (по умолчанию
  `10M`), **обрезает файл на месте**: самое старое стирается, а хвост — последние
  `LOG_KEEP_PERCENT` % (по умолчанию 10 %) — остаётся. Логи открыты в режиме
  `O_APPEND`, поэтому сервис продолжает писать в тот же файл: перезапуск не
  нужен, история не «прыгает». Раньше логи обрезались только при перезапуске
  стека (`.log` → `.log.1`), а долгоживущие процессы могли занять весь диск.
  Обрезать вручную: `./run.sh --rotate-now` (пригодится и из cron/таймера).
  Настройки — `LOG_MAX_SIZE`, `LOG_KEEP_PERCENT`, `LOG_CHECK_INTERVAL` в `.env`.
* **Данные и логи на разных дисках.** Каталоги задаются в `.env` (`DATA_DIR` —
  история Prometheus, база Grafana и pid-файлы; `LOG_DIR` — логи) и флагами
  установщика `--data-dir PATH` / `--log-dir PATH`; каталоги создаются
  автоматически. `stop.sh` и `status.sh` теперь тоже читают `.env`, поэтому
  находят pid-файлы и логи и при вынесенных каталогах, а `run.sh` печатает
  предупреждение, если каталог оказался на системном диске (`/`) — типичный
  симптом несмонтированного диска.
* `status.sh` показывает каталог логов, размер каждого файла и работает ли
  ротатор; правило logrotate ставится на реальный `LOG_DIR` (а не на `data/`).

### Изменено

* Ротация больше не создаёт архивы `.log.1…N` при каждом запуске (это осталось
  за logrotate: неделя × 8 со сжатием) — в текущем файле остаётся хвост
  последних записей.
* Установщик кладёт рядом с проектом `.env.example` и каталог `tools/` — на них
  ссылаются `docs/configuration.md` и README, но раньше они не копировались.

### Совместимость

* **Обновление с 1.3.0 и старше ничего не ломает.** Новые ключи `.env`
  необязательны: без них `DATA_DIR`/`LOG_DIR` — это прежний `data/`, накопленная
  история Prometheus и база Grafana остаются на месте, `.env` установщик не
  переписывает (недостающие ключи только дописывает, и то лишь заданные).
  `read_version`-строки (`SNMP_VER`/`PROM_VER`/`GF_VER`) и маркеры, которые
  правит `patch_run_sh`, не менялись — установка прошлых версий (`--ref v1.3.0`)
  работает как раньше.
* **Смешанные версии.** Новый `run.sh` + старый `stop.sh`: ротатор не
  останавливается, но вреда нет — он только обрезает логи, а следующий
  `run.sh` найдёт его по `LOG_DIR/rotate.pid` и не поднимет второй. Старый
  `run.sh` + новые `stop.sh`/`status.sh`: pid-файлы сервисов ищутся и в
  `<каталог>/data` (там их писал `run.sh` до 1.4.0), а `status.sh` честно
  сообщает, что `run.sh` этой версии не умеет обрезать логи по размеру.
* **Поведение Grafana не менялось**: штатный режим логирования в Grafana —
  `console`, он и оставлен (переопределяется `GF_LOG_MODE` в `.env`). Если
  файловый лог Grafana был включён явно, файл теперь лежит в `LOG_DIR/grafana/`
  и тоже обрезается по размеру.
* Правило logrotate после обновления перезаписывается на `LOG_DIR` (для
  прежних установок это тот же `data/`) и дополнительно покрывает
  `LOG_DIR/*/*.log` — вложенные логи Grafana.

## [1.3.0] — 2026-09-29

### Добавлено

* **Дашборд: сводка по парку и отдельная вкладка на каждый ИБП.** Раньше все
  устройства были в одном полотне панелей — с ростом парка это становилось
  неудобным. Теперь сверху 8 счётчиков по всему парку (всего, в сети, нет связи,
  от батареи, низкий заряд, перегрузка, байпас, тревоги), ниже таблица «один ИБП =
  одна строка» с сортировкой «проблемные сверху» и две полосы истории за 24 часа,
  а под ними — вкладка на каждое устройство: паспорт, идентификация (`upsIdent*`,
  `upsInputLineBads`), 12 текущих значений и 4 графика. Вкладки создаются сами:
  строка повторяется по метке `instance` (`repeat`), поэтому отдельный дашборд на
  устройство не нужен, а свёрнутые вкладки Prometheus не опрашивают — 30 вкладок
  работают так же быстро, как две. Клик по имени ИБП в таблице оставляет на
  дашборде только его вкладку. Файл: `grafana/dashboards/ups-overview.json`.
* **Документ [docs/dashboard.md](docs/dashboard.md)** — из чего состоит дашборд,
  что означает каждый счётчик и каждая колонка, как добавить ИБП, почему панель
  может быть пустой.
* **CI в GitHub Actions** (`.github/workflows/ci.yml`): синтаксис bash,
  `shellcheck`, разбор JSON дашборда, проверка YAML, `promtool check config`,
  загрузка `snmp.yml` экспортёром и проверка всех PromQL-выражений дашборда.
* **Лицензия MIT** (`LICENSE`).

### Совместимость

* **Обновление и откат версии не теряют данные.** Дашборд и правила алертов —
  файлы провижининга без собственного состояния: метки (`instance`, `ups_ip`,
  `location`) и метрики UPS-MIB остаются теми же, поэтому история Prometheus и
  база Grafana (`data/`), `.env` и `targets.yml` при смене версии в обе стороны
  не затрагиваются. Отдельно откатить дашборд можно одним файлом (см.
  [docs/dashboard.md](docs/dashboard.md)).
* **Дашборд терпим к старой версии сервера.** Он не требует ничего, чего не было
  бы в 1.1.0: на установке 1.0.0 (там нет ни `ups_ip`, ни имён в `instance`, ни
  метрик идентификации и тревог) вкладки называются по IP, колонки «IP» и
  «Тревоги» не появляются, а значения показываются как «—». Дашборд при этом
  открывается и работает, миграции не нужны.
* **Скрипты не зависят от флагов новых версий.** `run.sh` не передаёт
  `stop.sh --timeout` (таймаут задаётся в самом `stop.sh`, по умолчанию 20 с),
  поэтому смешанные версии `run.sh` + `stop.sh` не приводят к отказу остановки.

## [1.2.1] — 2026-09-22

### Исправлено

* **Скрипты врали про остановленные сервисы, если запущены не от root.**
  `status.sh`, `stop.sh` и `run.sh` определяли живость процесса через
  `kill -0`, а он не может послать сигнал чужому (root-овскому) процессу и
  возвращает ошибку — хотя сервис работает. В результате `./status.sh` без
  root показывал «ОСТАНОВЛЕН» при живом стеке, а `./stop.sh` — «не запущен».
  Теперь признак жизни берётся из `/proc/<pid>` (доступен всем), `kill -0`
  остаётся запасным вариантом для систем без procfs, а защита от
  переиспользования PID (сверка имени процесса) сохранена.

## [1.2.0] — 2026-09-22

### Добавлено

* **Шардинг опроса (`SNMP_SHARDS`)**: в `.env` задаётся число процессов
  `snmp_exporter` (1..8), `run.sh` запускает их на портах
  `SNMP_EXPORTER_PORT`…`+N-1`, а Prometheus раскладывает ИБП между ними
  правилом `hashmod` — автоматически и детерминированно (устройство всегда
  попадает в свой шард). Раньше это требовалось делать руками правкой
  `prometheus.yml` и отдельным systemd-юнитом.
* **Рабочая конфигурация Prometheus** `data/prometheus.yml`: собирается при
  каждом запуске из `prometheus.yml` — подставляет адреса процессов
  экспортёра, правила шардинга и абсолютный путь к `targets.yml`.
* `status.sh` показывает шарды и распределение ИБП по ним
  (`распределение ИБП по шардам (штук:порт): 62:9116 58:9117`), а также какой
  конфиг реально использует Prometheus. У каждого шарда свой лог
  `data/snmp_exporter-N.log`.

### Изменено

* Смена `SNMP_EXPORTER_PORT` больше не требует правки `prometheus.yml` — порт
  подставляется автоматически, предупреждение из `run.sh` убрано.
* `run.sh` (`--foreground`) следит за всеми шардами: упавший перезапускается
  через `RESTART_DELAY`, `stop.sh` гасит все, включая процессы, оставшиеся
  после уменьшения `SNMP_SHARDS`.
* `install.sh` добавляет `SNMP_SHARDS` в `.env` (и в новые, и в существующие
  установки).

### Исправлено

* **Установщик оставлял сервис выключенным.** При обновлении он останавливает
  работающий стек (`systemctl stop` + `stop.sh`), а если затем запуск не
  выполнялся (`--no-start`, `--no-systemd`) или установка прерывалась на
  середине, никто не сообщал, что мониторинг лежит. Теперь установщик помнит,
  что сервис был активен, и в конце (или при выходе с ошибкой) печатает прямое
  предупреждение с командой запуска.
* `${!key}` в `ensure_env_keys` падал под `set -u`, если переменной нет в
  окружении (проявилось на новом ключе `SNMP_SHARDS`); дописываемые в `.env`
  ключи больше не дублируются — раньше вторая пустая строка могла затереть уже
  настроенный токен Telegram.

### Проверено

Стенд из 8 эмуляторов ИБП: `SNMP_SHARDS=1` — все цели на одном порту;
`=2` — распределение 2/6; `=3` — 3/4/1; во всех режимах `up=1` у всех ИБП,
падение шарда приводит к перезапуску, `stop.sh` освобождает все порты,
нечисловое значение `SNMP_SHARDS` откатывается к 1 с предупреждением.

## [1.1.1] — 2026-09-22

### Исправлено

* **Установщик не мог поставить предыдущую версию.** Он требовал файл
  `status.sh` (появился только в 1.1.0) и всегда создавал systemd-юнит с
  `run.sh --foreground`, которого в старых версиях нет. Теперь обязательны
  только те файлы, что есть в любой версии, а тип юнита выбирается по
  возможностям `run.sh`: для старых версий — прежняя схема (`Type=oneshot`)
  с честным предупреждением, что автоперезапуск при падении работать не будет.
  Проверено установкой v1.0.0 и v1.1.0 текущим установщиком.

После этого откат и возврат работают в обе стороны:

```bash
# откатиться на предыдущую версию
... | sudo bash -s -- --yes --ref v1.0.0
# вернуться на актуальную
... | sudo bash -s -- --yes --ref v1.1.1
```

## [1.1.0] — 2026-09-22

Первый выпуск с алертами, нормальной эксплуатацией и документацией.

### Добавлено

* **Алерты (7 правил)** в Grafana: ИБП недоступен, работа от батареи, низкий
  заряд, мало времени автономии, перегрузка, перегрев, медленный опрос.
* **Панели доступности** на дашборде: «Доступность ИБП (SNMP)» и «История
  доступности» — недоступное устройство больше не «исчезает» молча.
* **Тренды на дашборде**: заряд, нагрузка, температура, входное и выходное
  напряжение, остаток автономии за сутки + timeline «когда работал от батареи».
* **Уведомления в Telegram** (по умолчанию выключены, включаются в `.env`).
* **Режим супервизора** `run.sh --foreground`: перезапускает упавший сервис;
  systemd теперь замечает падения (`Restart=on-failure`).
* **`status.sh`** — состояние стека одной командой.
* **`tools/targets-from-csv.sh`** — сборка `targets.yml` из таблицы инвентаря.
* **Идентификация устройств**: `upsIdent*`, `upsInputLineBads`, `upsAlarmsPresent`.
* **Настройки в `.env`**: порты, `LISTEN_ADDR`, срок хранения истории
  (`RETENTION_TIME`, `RETENTION_SIZE`), пауза перезапуска.
* **Документация**: `docs/install.md`, `configuration.md`, `alerts.md`,
  `operations.md`, `troubleshooting.md`, `scaling.md`, `security.md`,
  `CHANGELOG.md`, а также `ROADMAP.md` с очередью доработок.
* **Разные учётки SNMP** в одном пуле: метки `snmp_auth` и `snmp_module`,
  пример SNMP v3, пароли через переменные окружения.

### Изменено

* **`instance` = имя ИБП** (`ups_name` из `targets.yml`), адрес — в метке
  `ups_ip`. При смене IP история больше не теряется. Если имя не задано,
  `instance` остаётся IP.
* **Таймауты опроса**: `timeout: 2s`, `retries: 1` (было 5s × 4 попытки) —
  недоступный ИБП занимает 4 секунды вместо 20.
* **Остановка** стала аккуратной: `SIGTERM` → ожидание завершения → `SIGKILL`,
  с проверкой имени процесса и остановкой супервизора.
* **Ротация логов** `data/*.log` (неделя × 8, сжатие) настраивается установщиком.
* Установщик помнит установленную версию (`.installed-ref`) и использует её при
  повторном запуске, если не указан `--ref` — обновление больше не «уезжает»
  на `main` само по себе.

### Исправлено

* Числовой `TELEGRAM_CHAT_ID` и пустой токен ломали запуск Grafana — контакт-поинт
  теперь создаётся из шаблона подстановкой текстом.
* Необязательные OID (`upsIdent*`, `upsAlarmsPresent`) при опросе через `get`
  отключали устройство целиком — перенесены в `walk`, такие ИБП опрашиваются
  нормально, просто без этих метрик.
* `stop.sh` мог не освободить порты и «возрождал» сервисы при работающем
  супервизоре.

## [1.0.0] — 2026-09-21

Первый выпуск: мониторинг ИБП по SNMP без Docker — `snmp_exporter` +
Prometheus + Grafana обычными процессами.

* `run.sh` / `stop.sh`: скачивание бинарников и запуск трёх сервисов, без Docker
  и без Python;
* дашборд «ИБП — обзор» (заряд, напряжение, нагрузка, температура, статус);
* список ИБП в `targets.yml` с авто-перечитыванием (метки `ups_name`, `location`);
* модуль `ups` в `snmp.yml` на стандартных OID UPS-MIB (RFC 1628), community `public`;
* `install.sh`: установка на сервер одной командой, проверка sha256, автозапуск
  через systemd, интерактивная настройка и флаги.
